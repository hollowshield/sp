How to donut

a1k0n's donut.c is one of the most famous tiny programs on the internet. Here's exactly why it works, and then how to move the same math out of the terminal and into a real window.

Time
About 30 minutes
You need
A C++ compiler and GLFW
You'll make
A spinning donut, then any image in 3D
Code
hollowshield/donutDemo

On this page

Here, have a donut

This is a 3D donut drawn with nothing but text. No graphics library, no triangles, no ray tracing: just a grid of characters, a little trigonometry and a few lines of C++.

The sliders are the program's constants. You'll learn what each one does below; come back and play with them once you have. Try dragging R2 down to 0.

The plan: five ideas make the math work, then we keep every bit of that math and only change where the pixels go.

1. Projection: similar triangles do the work

Picture yourself looking through a screen at a point in space. The line from your eye to the point crosses the screen somewhere, and that's where you draw it.

Because the triangles are similar, their sides keep the same ratio:

y' / K1 = y / z    →    y' = K1 * y / z
x' / K1 = x / z    →    x' = K1 * x / z

K1 is the distance from your eye to the screen, so it works as the zoom. That one division is the entire camera.

Try it: with K1 = 10, a point at y = 2, z = 4 lands at y′ = 10 × 2 / 4 = 5. Push it back to z = 8 and it lands at 2.5. Farther away means closer to the center of the screen, which is exactly what perspective looks like.

Watch it happen

This is projection.cpp from the workshop, running in your browser. Step through it: it starts with one dot and ends with a spinning triangle that is really just three dots moving left, right, up and down.

2. Depth: who's in front?

Many points on the donut land on the same character cell, for example the front and back of the ring. A z-buffer remembers how close the last thing drawn in each cell was, and a new point only wins if it's closer.

// every frame
std::fill(zBuf, zBuf + W*H, 0.0f);   // 0 = infinitely far

// every point
float invZ = 1 / z;                  // divide once...
int xp = W/2 + K1 * x * invZ;        // ...reuse for x'
int yp = H/2 - K1 * y * invZ;        // ...and y'
int o  = xp + W * yp;                // which cell
if (invZ > zBuf[o]) { zBuf[o] = invZ; draw(o); }
Store 1/z, not z
A bigger 1/z means closer. Clear the buffer to 0 and empty cells are automatically "infinitely far away".
Divide once
The same 1/z feeds both x′ and y′, so you trade two divisions for one division and two multiplications.

3. The shape: a circle, swept around an axis

A donut (a torus) is what you get when you spin a circle around an axis that doesn't go through it. Two angles reach every point on the surface:

  • θ walks around a small circle of radius R1, centered at (R2, 0, 0):
    (R2 + R1·cos θ, R1·sin θ, 0)
  • φ spins that circle around the y axis:
    ((R2 + R1·cos θ)·cos φ, R1·sin θ, −(R2 + R1·cos θ)·sin φ)

donut.c uses R1 = 1 and R2 = 2.

4. Rotation: then spin the whole thing

Three standard rotation matrices do the work. The first one is the φ sweep from the last section; A and B are the animation angles, nudged a little every frame.

Multiply them out once by hand (or with a computer algebra system) and every zero becomes a term you never compute. That's where the long formulas in the code come from:

const float x = circlex * (cosB * cosphi + sinA * sinB * sinphi) - circley * cosA * sinB;
const float y = circlex * (sinB * cosphi - sinA * cosB * sinphi) + circley * cosA * cosB;
const float z = K2 + cosA * circlex * sinphi + circley * sinA;

5. Shading: how bright is this spot?

  • The normal. The direction the surface faces. Start from (cos θ, sin θ, 0) on the small circle and apply the same three rotations.
  • The light. Pick (0, 1, −1): above and behind you. The dot product of the normal with the light is how directly the surface faces it.
  • The character. That brightness, L, runs from −√2 to √2. Skip L ≤ 0 (facing away from the light), and pick a character from a 12-step ramp:
".,-~:;=!*#$@"[(int)(L * 8)]   // 8 × √2 ≈ 11.3, so the index never runs off the end

The light vector isn't normalized (its length is √2), which is why the code multiplies by 8 instead of 12.

Putting it together: the render loop

for (θ = 0; θ < 2π; θ += 0.07)
  for (φ = 0; φ < 2π; φ += 0.02) {
    p    = rotate(torus(θ, φ), A, B);    // shape + rotation
    invZ = 1 / (p.z + K2);               // divide once
    xp   = W/2 + K1 * invZ * p.x;        // projection
    yp   = H/2 - K1 * invZ * p.y;        // screen y points down
    L    = brightness(θ, φ, A, B);       // shading
    if (L > 0 && invZ > zBuf[yp][xp]) {  // depth
      zBuf[yp][xp] = invZ;
      out[yp][xp]  = ".,-~:;=!*#$@"[(int)(L * 8)];
    }
  }

Precompute the sine and cosine of A and B once per frame. Note the minus sign on y: in 3D, y points up, but screen rows count down.

Animating in a terminal

  1. Once, at startup: clear the screen (\x1b[2J) and hide the blinking cursor (\x1b[?25l).
  2. Every frame, render: run the donut math into a character buffer. Nothing touches the screen yet.
  3. Every frame, draw: move the cursor home (\x1b[H), write the whole frame in one call, spin a little, repeat.

Why one write? Printing line by line lets the terminal show half-drawn frames, and the cursor flickers down the left edge. Build the frame first, write it once.

Why do x and y get different zooms? Character cells are about twice as tall as they are wide, so y gets a smaller K1 than x. Otherwise the donut comes out stretched.

Show the full terminal donut (DonutTerminal.cpp)

Build it with g++ -std=c++17 -O2 DonutTerminal.cpp -o donutTerm and run it in a terminal at least 80 columns wide. Ctrl+C quits.

Hello, window

        
OpenGL only draws. GLFW opens the window, reads input, and hands OpenGL a place to draw.

        
#include <GLFW/glfw3.h>

int main() {
  glfwInit();
  GLFWwindow* win = glfwCreateWindow(800, 600,  // 1 open
                    "Donut", nullptr, nullptr);
  glfwMakeContextCurrent(win);

  while (!glfwWindowShouldClose(win)) {
    glfwPollEvents();                           // 2 events
    glClearColor(0.04f, 0.11f, 0.18f, 1.0f);    // 3 draw
    glClear(GL_COLOR_BUFFER_BIT);
    glfwSwapBuffers(win);                       // 4 present
  }
  glfwTerminate();
}

    2. 
          
  2. Events: glfwPollEvents handles keys, the mouse and the close button.
    3. 
          
  3. Draw: gl* calls draw into a hidden back buffer.
    4. 
          
  4. Present: glfwSwapBuffers shows the finished frame.

The payoff: the donut gets pixels

        


// once, before the loop
unsigned char pixels[W * H * 3];   // R, G, B per pixel
float zbuf[W * H];

// each frame: clear both, then for each point...
float shade = 0.2f + 0.8f * L;
int o = xp + W * yp;
if (invZ > zbuf[o]) {
    zbuf[o] = invZ;
    pixels[3*o]   =  46 * shade;   // ACM blue,
    pixels[3*o+1] = 168 * shade;   // darker when
    pixels[3*o+2] = 240 * shade;   // facing away
}

// ...then hand the buffer to OpenGL
glDrawPixels(W, H, GL_RGB, GL_UNSIGNED_BYTE, pixels);
glfwSwapBuffers(win);

          

            
Mind the holes
A window has far more pixels than a terminal has cells. Sample more points, or paint each point as a 2×2 block.

            
Row 0 is the bottom
OpenGL starts at the bottom-left, so drop the minus sign: yp = H/2 + K1·invZ·y.

            
One K₁ again
Pixels are square, so x and y share the same zoom.

            Answer: Color it
            

              
A normal's x, y and z each run from −1 to 1. Remap them to 0 to 1 and use them as red, green and blue, then darken with the usual shading. In render(), replace the three color lines:


// color from the rotated normal: each axis -1..1 becomes 0..1
float cr = 0.5f + 0.5f * n.x;
float cg = 0.5f + 0.5f * n.y;
float cb = 0.5f + 0.5f * n.z;
unsigned char r = (unsigned char)(255 * std::min(1.0f, cr * shade));
unsigned char g = (unsigned char)(255 * std::min(1.0f, cg * shade));
unsigned char b = (unsigned char)(255 * std::min(1.0f, cb * shade));

              
Because the normal is rotated with the donut, the colors stay stuck to the surface as it spins.

            

          


          

            Answer: Drive it
            

              
Key callbacks only fire when a key goes down or up. For "while held", ask GLFW each frame with glfwGetKey. Replace the automatic spin in the main loop, and delete the Space line from onKey so the two don't fight:


const float speed = 1.5f;   // radians per second
if (glfwGetKey(win, GLFW_KEY_UP)    == GLFW_PRESS) A -= speed * dt;
if (glfwGetKey(win, GLFW_KEY_DOWN)  == GLFW_PRESS) A += speed * dt;
if (glfwGetKey(win, GLFW_KEY_LEFT)  == GLFW_PRESS) B -= speed * dt;
if (glfwGetKey(win, GLFW_KEY_RIGHT) == GLFW_PRESS) B += speed * dt;

bool holdingSpace = glfwGetKey(win, GLFW_KEY_SPACE) == GLFW_PRESS;
if (!holdingSpace) { A += 0.7f * dt; B += 1.2f * dt; }   // keep spinning unless held

            

          


          

            Answer: Resize it
            

              
GLFW windows are resizable by default; the fixed-size arrays are what stop the donut from following. Make the buffer size variables and the arrays vectors:


int BW = 400, BH = 300;
std::vector<unsigned char> pixels(BW * BH * 3);
std::vector<float>         zbuf(BW * BH);

void resizeBuffers(int fbWidth, int fbHeight) {
    BW = std::max(1, fbWidth / 2);    // keep the chunky 2x look (use fbWidth for full resolution)
    BH = std::max(1, fbHeight / 2);
    pixels.assign(size_t(BW) * BH * 3, 0);
    zbuf.assign(size_t(BW) * BH, 0.0f);
}

// in the main loop, right after glfwGetFramebufferSize(win, &fw, &fh):
if (fw / 2 != BW || fh / 2 != BH) resizeBuffers(fw, fh);

              
In render(), use pixels.data() where it used pixels, and clear with std::fill(zbuf.begin(), zbuf.end(), 0.0f). K1 is already computed from BH every frame, so the zoom follows the new height for free.

            

          


          

            Answer: New shape
            

              
With R2 = 0, the small circle is centered on the axis it spins around, so sweeping it traces out a sphere. You can try it with the R2 slider at the top of the page.

              
For two donuts, split render() into a clear step and a draw step, and only clear once per frame. Because both donuts write into the same z-buffer, wherever they pass through each other the nearer surface wins pixel by pixel, so they intersect correctly for free:


void clearBuffers() {
    for (int i = 0; i < BW * BH; i++) { pixels[3*i] = 10; pixels[3*i+1] = 27; pixels[3*i+2] = 46; }
    std::fill(zbuf, zbuf + BW * BH, 0.0f);
}

// drawModel = the old render() without the clearing, plus an offset applied after rotating
void drawModel(const Model& m, float A, float B, Vec3 offset) {
    // ... same as before, but:
    Vec3 p = rotate(s.p, cA, sA, cB, sB);
    p = { p.x + offset.x, p.y + offset.y, p.z + offset.z };
    // ... project, shade and depth-test exactly as before
}

// each frame:
clearBuffers();
drawModel(model, A, B,        { -1.5f, 0.0f, 0.0f });
drawModel(model, A + 1.0f, B, {  1.5f, 0.0f, 0.0f });
