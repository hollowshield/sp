Impossible Connect 4

Building an AI that never loses, step by step: a window, a two-player game, then a search that plays perfect Connect 4 fast enough to feel instant.

Time
About 60 minutes
You need
A C++ compiler and SDL3
You'll learn
Game loops, minimax, alpha-beta, bitboards
Code
hollowshield/ImpossibleConnect4

On this page

Why build this?

One July afternoon, I played Connect 4. I kept losing. I now hate Connect 4. The solution: make everyone else suffer, by building a Connect 4 that is impossible to beat.

That's less of a stretch than it sounds, because Connect 4 is a solved game: with perfect play, the player who moves first can always force a win.

  1. Oct 1, 1988 · James D. AllenAnnounces the first (weak) solution on rec.games.programmer.
  2. Oct 16, 1988 · Victor AllisAnnounces his independent solution, described in his thesis.
  3. Later · John TrompStrongly solves it with a database of every 8-ply position: about 40,000 hours of computation at CWI.

In this project's normal mode the AI moves first, so if it plays perfectly, it cannot lose. The whole challenge is playing perfectly fast enough to be fun.

Weakly solved vs. strongly solved

Weak (Allen and Allis, 1988)
You know who wins from the starting position, and a strategy that gets that result.
Strong (Tromp's 8-ply database)
You know the result of every possible position, so you can play perfectly from anywhere.
What this AI does: no giant database that takes thousands of hours to build. A small opening book of about 1,040 positions makes the first few moves instant, and after that the AI searches for the perfect move on its own. It behaves like a strong solution, computed on demand.

Part 1: The SDL3 window

From an empty program to a window that draws the board 60 times a second.

Every SDL program has the same lifecycle

  1. InitializeStart the video subsystem with SDL_Init
  2. CreateOne call makes the 700 × 600 window and its renderer
  3. LoopHandle events, update, draw. Repeat until quit
  4. Clean upDestroy the renderer, then the window, then SDL_Quit
  • SDL3 gotcha: SDL_Init returns true on success. SDL2 returned 0 on success, so SDL2 tutorials get this backwards.
  • The grid sets the window size: 7 columns × 100 px by 6 rows × 100 px. The board defines the window, not the other way around.

The game loop

while (!quit) {
    while (SDL_PollEvent(&e)) {
        if (e.type == SDL_EVENT_QUIT)
            quit = true;
        // mouse motion, clicks, R and E keys
    }

    // start or collect the AI's move

    renderBoard(renderer, hoveredCol);
    SDL_Delay(16);   // about 60 FPS
}
Poll every frame
SDL_PollEvent empties the event queue without waiting. Stop polling and the OS marks your window "Not Responding". (Remember this for Part 3.)
Cap the frame rate
SDL_Delay(16) gives about 60 FPS. The usual alternative is vsync.
Renamed in SDL3
SDL_QUIT is now SDL_EVENT_QUIT, and the other events follow the same pattern.

Drawing a frame

  1. Clear: SDL_SetRenderDrawColor, then SDL_RenderClear.
  2. Draw: a blue square per cell (SDL_FRect, which uses floats in SDL3), then a disc on top.
  3. Present: SDL_RenderPresent swaps the hidden back buffer onto the screen.

That's double buffering: everything is drawn off-screen and shown all at once, so nobody sees a half-drawn frame. SDL has no built-in text, so the title bar works as the UI: updateTitle() shows whose turn it is and who won, with no need for SDL_ttf.

Drawing a circle

SDL3 can only fill rectangles, so the discs are drawn pixel by pixel: check every pixel in the square around the circle, and draw it if it's within the radius. Drag the slider to see which pixels pass the test.

// Draw a filled circle pixel by pixel
// (SDL3 has no circle primitive, only rectangles)
void DrawFilledCircle(SDL_Renderer* renderer,
                      float centerX, float centerY,
                      float radius) {
    for (float w = 0; w < radius * 2; w++) {
        for (float h = 0; h < radius * 2; h++) {
            float dx = radius - w;
            float dy = radius - h;
            if ((dx * dx + dy * dy) <= (radius * radius)) {
                SDL_RenderPoint(renderer, centerX + dx,
                                centerY + dy);
            }
        }
    }
}

Part 2: Player vs. player

Turning the window into a game: the board in memory, gravity, and finding four in a row. Play a game below and watch the array the program actually stores.

  • Row 0 is the top. That matches screen coordinates, so cell (r, c) is drawn at y = r × 100 with no flipping.
  • Red (PLAYER1) always moves first.

From a click to a dropped piece

int col = static_cast<int>(e.button.x)
          / CELL_SIZE;   // 0-699 → 0-6

bool makeMove(int col) {
    if (col < 0 || col >= COLS) return false;
    for (int r = ROWS - 1; r >= 0; r--) {
        if (board[r][col] == EMPTY) {
            board[r][col] = currentPlayer;
            return true;
        }
    }
    return false;   // column is full
}
Click → column
Integer division maps a pixel to a column.
Gravity
makeMove() scans from the bottom row up for the first empty cell. A full column returns false, and since the turn only switches after a successful move, clicking a full column does nothing.
Hover highlight
Mouse-motion events set hoveredCol the same way, and SDL_EVENT_WINDOW_MOUSE_LEAVE clears it.

Finding four in a row

// right: same row, the next 3 columns
if (c + 3 < COLS &&
    board[r][c + 1] == currentPlayer &&
    board[r][c + 2] == currentPlayer &&
    board[r][c + 3] == currentPlayer) return true;
// ...and the same for down, down-right and up-right
  • Why only 4 directions? The other 4 are the same lines seen from the other end. Checking from every cell covers them.
  • Why only the current player? Only the player who just moved can have won.

42 cells is tiny, so scanning the whole board after every move is fine here. Keep this loop in mind: the AI does the same job with bit shifts later.

One move, start to finish

  1. Place the piecemakeMove(col)
  2. Did they win?Yes: game over
  3. Board full?Yes: draw
  4. Switch playersNext turn

Order matters: applyMove() checks for a win before switching players. Switch first and you'd check the wrong player.

Part 3: The AI

How a program can play a perfect game of Connect 4 in a reasonable amount of time.

Plugging the AI into the game

Two copies of the board
board[6][7] for drawing, and a c4::Position bitboard for the AI. makeMove() updates both, which keeps them in sync.
Who goes first
Red always moves first. Normal mode: the AI is red. Easy mode: you are red.
Main thread
Keeps polling events and drawing. Every frame it checks with wait_for(0) whether the AI is done.
AI thread
std::async runs solver.bestMove() on a copy of the position, so it never reads a board that's changing.

A search can take seconds. If it ran inside the game loop, the loop would stop polling and the window would freeze. While the AI is thinking, clicks and the R and E keys are ignored, and on quit, solver.abort tells the search to stop so the program exits cleanly.

Why not just try every game?

Because there are far too many. Possible positions on a 6-row board, by width:

4,531,985,219,092 positions on a standard 7 × 6 board, counted by John Tromp and independently confirmed by Edelkamp and Kissmann in 2008. Brute force is out, so the solver has to be clever: skip branches that can't matter, never solve the same position twice, and make every operation cheap.

Keeping score

Each position gets a score from the point of view of the player about to move:

score = 22 - (your stones when you win)
  • > 0, a win. Bigger means a faster win. Winning with your 4th stone scores 22 − 4 = 18.
  • = 0, a draw. Nobody can force a win.
  • < 0, a loss. Closer to 0 means a slower loss.

Because the score encodes how fast the game ends, the AI can prefer quick wins and slow losses. In code, canWinNext() gives (43 - movesPlayed) / 2, and scores range from −21 to 21.

Negamax: one function for both players

Minimax: I pick my best move, assuming you pick the move that's worst for me. Negamax is the same idea with one trick: +5 for me is −5 for you, so a single function handles both players by flipping the sign.

int negamax(const Position& P, int alpha, int beta) {
    uint64_t next = P.possibleNonLosingMoves();
    if (next == 0)                         // every move loses
        return -(42 - P.movesPlayed()) / 2;
    if (P.movesPlayed() >= 40) return 0;   // draw

    // ... bounds, transposition table, sort moves ...

    while (uint64_t move = sorter.next()) {
        Position P2(P); P2.play(move);
        int score = -negamax(P2, -beta, -alpha);   // your best is my worst
        if (score >= beta) return score;           // cutoff
        if (score > alpha) alpha = score;
    }
    return alpha;
}

Alpha-beta pruning: skip what can't matter

Alpha
The score I'm already guaranteed.
Beta
The best score my opponent will allow.
The cutoff
Once a move scores ≥ beta, the opponent would never let the game get here. Skip the remaining moves.

Example: my move A guarantees me −1. In move B, the very first reply I look at shows my opponent can force −3, which is worse. So I'd never play B, and the rest of B's replies are never looked at.

Your turn

Watch pruning work

This AI uses the same negamax and alpha-beta ideas, but it's a simplified teaching version: it only looks a few moves ahead and then guesses, so it can be beaten. The table counts how many positions it searched for each move.

  • Try 1: Turn off pruningKeep look-ahead at 6 and compare the positions searched with and without alpha-beta.
  • Try 2: Turn off center firstPruning only helps when good moves are searched first. How much does move order matter?
  • Try 3: Beat itWin at look-ahead 2, then 4, then 6. Where does it stop making obvious mistakes?
What you should see

Try 1. Without pruning, every position up to the look-ahead gets searched: up to 7 × 7 × 7 … for each extra move. With pruning, the count usually drops by one or two orders of magnitude for the exact same move.

Try 2. Alpha-beta cuts more when the best move comes first, because it sets a strong alpha early. Center columns are part of the most possible fours, so searching them first finds good moves sooner; with plain left-to-right order the counts go up noticeably.

Try 3. At low look-ahead the AI can't see your traps coming. The real solver never guesses: it searches to the end of the game, which is why it needs everything below.

The opening book: answers computed in advance

The game tree is biggest at the start, so a perfect search is slowest exactly when players are least patient. Connect4Book.h stores about 1,040 positions with their best move, generated offline with the same solver, sorted by key and looked up with binary search. It covers every reply in the AI's first 5 moves, plus easy-mode replies to all 7 openings. Every book entry is a proven winning move.

Bitboards: the whole board in 49 bits

The search visits millions of positions, so checking a board has to be nearly free. The AI stores the board as two 64-bit numbers: mask (every stone) and current (the stones of the player to move). Each column gets 7 bits: 6 for the cells plus a spare bit on top that's always 0. Bit number = column × 7 + row from the bottom. Play below and watch both numbers change.

Why the spare bit? It catches the carry from a full column and stops horizontal and diagonal lines from wrapping into the next column. This encoding comes from John Tromp.

Bitboard tricks

Gravity by addition
(mask + bottomMask(col)) & columnMask(col). Adding 1 at the bottom of a column carries up through the stones and lands on the first empty cell. The board above shows the carry for every move you make.
Every playable cell at once
(mask + BOTTOM_MASK) & BOARD_MASK: the same trick, with a 1 at the bottom of all 7 columns in one addition.
Switching players
current ^= mask; XOR with all stones turns "my stones" into "your stones" before the move is added.
Finding wins with shifts
Shift by 1 for vertical, 7 for horizontal, 6 and 8 for the diagonals. ANDing shifted copies finds every empty cell that would complete a four (XXX_, XX_X, X_XX, _XXX).

Compare that with checkWin()'s loops from Part 2: the same job, done for the whole board in a handful of instructions. And current + mask is unique for every position, which makes it a perfect key.

Four tricks that make it fast enough

  1. Move ordering. Search the center first (COLUMN_ORDER = {3, 2, 4, 1, 5, 0, 6}), then sort by how many threats each move creates. Alpha-beta prunes more when good moves come first.
  2. Transposition table. The same position can be reached in different move orders. Store each result so it's never solved twice.
  3. Anticipate losing moves. Two threats: you're lost. One threat: you must block. Never play directly under the opponent's winning cell.
  4. Null-window search. Ask yes/no questions like "is the score above 0?" instead of computing exact scores. Much cheaper.

Each is a step in Pascal Pons's solver tutorial at blog.gamesolver.org.

Inside the transposition table

It's a hash map for game positions, like a chess player's memory of openings and gambits.

Slots16.7 million: a prime number just above 224
Per slot5 bytes: 32 bits of the key plus a 1-byte value
MemoryAbout 84 MB, reused across moves and games
The value byte0 = empty slot, 1–43 = an upper bound on the score, 44–86 = a lower bound (from a cutoff)

Why store only 32 of the 49 key bits? With a prime table size above 217, the slot number plus the 32 stored bits pin down the full key exactly (the Chinese remainder theorem). New results always overwrite the slot.

How the AI picks a move

  1. Check the opening book: instant answers for the early game.
  2. Take an immediate win: if any column wins now, play it.
  3. Keep only safe moves: drop moves that let the opponent win next turn.
  4. Look for a forced win: a yes/no search with the window (−1, 0).
  5. Otherwise, hold the draw: a yes/no search with the window (0, 1).
  6. If lost, delay: delayLoss() makes the opponent work as long as possible.

Step 4 plays the first winning move it finds, not always the fastest one. The AI still always wins.

Easy mode: giving humans a chance

  • You go first. Perfect play from the first player wins, so now a human can win.
  • A 3-second budget. The clock is checked every 1,024 positions; checking every single one would slow the search.
  • A heuristic fallback. Out of time? Play the safe move that creates the most threats.
  • Never store a half-finished search. Results from an interrupted search would be wrong, so they never go into the table.

Common questions

        

          
Does it work on bigger boards?
The bitboard needs width × (height + 1) ≤ 64 bits. John Tromp's page has results for other sizes; for example, 8 × 8 is a win for the second player.

          
Could machine learning do this instead?
People try. Tromp publishes a dataset of 67,557 positions with their results for exactly that.

          
How was the opening book made?
With the same solver, run offline over every position in the AI's first moves, then sorted by key so lookups are a binary search.
